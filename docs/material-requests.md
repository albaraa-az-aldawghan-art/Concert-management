# طلبات المواد الخام

توجد تحت **التكاليف ← طلبات المواد**، ومن رابط متابعة الطلبات في الوارد.

## دورة العمل

1. اختيار مواد خام مسجلة وتحديد الكمية بوحدة الشراء أو المخزون. تظهر الوحدتان ومعامل التحويل والرصيد والحد الأدنى والكميات المطلوبة سابقًا.
2. إرسال الطلب مباشرة دون خطوة اعتماد. الطلب لا يحرك المخزون أو التكلفة.
3. تسجيل ما وصل فعليًا على دفعة أو عدة دفعات. إدخال الكمية لا يفترض وصول جميع مواد الطلب.
4. إن كانت الفاتورة متوفرة، تُسجل معها ويُعتمد المخزون مرة واحدة. عند غيابها يُحفظ الوصول «بانتظار الفاتورة»، خارج الرصيد القابل للصرف.
5. إضافة رقم الفاتورة وتاريخها وسعر وحدة الشراء قبل الضريبة لكل مادة لاحقًا لاعتماد الكمية. السعر المفقود ليس صفرًا؛ الصفر يحتاج إدخالًا صريحًا.

المتبقي توريده = أقصى (المطلوب − المستلم − الملغى، 0). لا يساوي رصيد المستودع الحالي الذي يتأثر بالصرف والإنتاج والتالف. الزيادة المسموحة تُسجل بكميتها الفعلية ولا تجعل المتبقي سالبًا. الكميات المختلفة الوحدات لا تجمع في رقم واحد.

حالة «بانتظار الفاتورة» لها الأولوية عند وجود أي دفعة معلّقة، حتى لو بقيت مواد لم تصل؛ لذلك فلتر الفواتير المعلقة لا يفوّت الطلبات المستلمة جزئيًا. تبقى الكميات التفصيلية ظاهرة دائمًا.

## الطلب التلقائي

يُفعّل لكل صنف مع حد أدنى ورصيد مستهدف أكبر منه. عند انخفاض الرصيد للحد الأدنى:

`الكمية الجديدة = أقصى (المستهدف − الرصيد − المطلوب ولم يصل − الواصل بانتظار الفاتورة، 0)`

يعمل ضمن معاملات حركات المخزون على الخادم، بما فيها الصرف والتالف والإنتاج والوارد؛ لا يحتاج فتح الصفحة ولا خدمة مجدولة ولا نسخ قاعدة البيانات. تفعيل السياسة على صنف منخفض قد ينشئ طلبًا فورًا. تعطيلها لا يلغي الطلبات السابقة. الإلغاء لا ينشئ بديلًا فورًا؛ يمكن أن تؤدي حركة مخزون لاحقة إلى طلب جديد ما دامت السياسة مفعّلة.

## الصلاحيات

`mat_view` لطلباته، `mat_view_all` للجميع (يلزم لموظف الوارد الذي يتابع طلبات الآخرين والتلقائية)، `mat_create`، `mat_edit` قبل الاستلام، `mat_receive` للوصول، `mat_invoice` لاعتماد الفاتورة، `mat_overreceive` للزيادة، `mat_cancel` للمتبقي، `mat_correct` لعكس دفعة، `mat_auto` للسياسة، و`mat_price` لعرض الأسعار. صلاحية تسجيل الفاتورة تتيح إدخال السعر، وعرض الأسعار التاريخية منفصل. الأدمن يملكها جميعًا. الأدوار الموجودة لا تُمنح صلاحيات إضافية تلقائيًا.

## السلامة والتصحيح

- الاستلام والفاتورة وتحديث المخزون والتغطية تحفظ ذريًا. معرف العملية يمنع تكرار الإضافة عند إعادة المحاولة.
- لا يُعدل الطلب بعد بدء استلامه؛ قبل ذلك يلزم تطابق إصدار التعديل لمنع فقدان عمل موظف آخر.
- إلغاء المتبقي لا يمس الدفعات الواصلة التي ما زالت تحتاج فاتورة.
- تصحيح دفعة معلقة يعيد فتح كميتها. عكس دفعة معتمدة ممنوع بعد صرف المادة؛ نفس سياسة حماية المتوسط الموجودة في الوارد الحالي.
- الوارد المرتبط لا يُحذف منفردًا من شاشة الوارد؛ التصحيح عبر الطلب للمحافظة على تطابق جميع السجلات.
- تُحفظ وحدات ومعامل التحويل وقت الطلب، فلا تعيد التغييرات اللاحقة تفسيره. تغيير نوع/وحدة مادة لها طلب غير مكتمل ممنوع. حذف مادة ذات تاريخ طلبات ممنوع.
- لا ربط تلقائي بين الفواتير القديمة أو الوارد المستقل وهذه الطلبات. استلم الطلب من مساره المرتبط.

## البيانات والفهارس

المجموعتان الجديدتان `cost_material_requests` و`cost_material_receipts`، وحقول تغطية وسياسة اختيارية داخل `cost_items`. الحسابات القديمة لا تحتاج ترحيلًا، والتلقائي معطل افتراضيًا. كل القراءة والكتابة للمجموعتين عبر API محمي؛ لا وصول مباشر للمتصفح، وتُحذف الأسعار من استجابة غير المخول.

القائمة تجلب حتى 20 طلبًا مع سجل إضافي لمعرفة وجود صفحة تالية. فلاتر الحالة والتاريخ وصلاحية المالك والبحث تطبق قبل التقسيم. البحث يدعم بداية الاسم أو كلمة منه أو الباركود حتى 64 حرفًا، وليس بحثًا حرًا في منتصف كل كلمة. التفاصيل والدفعات تحمل عند الطلب؛ اختيار المواد يجلب حقول المخزون دون أسعارها.

نشر الفهارس فقط دون قراءة بيانات العمل:

```powershell
firebase deploy --only firestore:indexes --project concert-management-a4fea --non-interactive
```

يتطلب النشر جلسة Firebase CLI مخوّلة بإدارة الفهارس. التحقق دون قراءة بيانات العمل: `node scripts/deploy-material-indexes.mjs`، حتى تصبح جميع الفهارس `READY`.

## الاختبارات

### الأقسام والتوجيه وطباعة PDF

- الأقسام التنظيمية هي المطعم والحفلات والتعاقدات. «عام» يعني جميع المواد وليس قسمًا رابعًا تُصنّف تحته المادة. من زر **أقسام المواد** يمكن اختيار أكثر من قسم لكل مادة خام. غير المصنّف يظهر في عام فقط، ولا يُستنتج القسم من الاسم أو قناة البيع.
- عند إنشاء/تعديل طلب تختار قسم الطلب أولًا، ثم تظهر مواده فقط. الخادم يتحقق من الانتماء مرة أخرى. تغيير القسم لا يحذف سطورًا مُدخلة تلقائيًا؛ يلزم إزالة السطور غير التابعة أولًا لحفظ الكميات من الفقد غير المقصود.
- التصنيف لا يغيّر المخزون أو أسعاره أو قناة المنصرف أو تكاليف العقود والحفلات. الطلبات التلقائية تبقى عامة وغير موجّهة حتى يوجّهها موظف مخوّل؛ لا تُنشأ طلبات تلقائية متعددة لنفس النقص بسبب تعدد الأقسام.
- يمكن توجيه الطلب لحساب موظف مسجل أو إلغاء التوجيه. يرى الطلب منشئه والموجّه إليه ومن لديه عرض جميع الطلبات. إزالة التوجيه تسحب وصول الموظف السابق ما لم يكن المنشئ أو لديه عرض الكل. صلاحية عرض طلباته `mat_view` ووصول صفحة التكاليف ما زالا مطلوبين؛ التوجيه لا يمنح أفعال الاستلام والفاتورة.
- اختيار الموظفين يعرض المعرّف والاسم فقط دون البريد أو الصلاحيات. يُتحقق من وجود الموظف مجددًا داخل معاملة الحفظ. يمكن تغيير التوجيه بعد استلام الطلب دون تعديل المخزون أو الفواتير، مع حماية التعديل المتزامن.
- كل طلب في المتابعة لديه زر PDF، ومنه اختيار قسم الطباعة. عام يطبع كل مواد الطلب؛ القسم المحدد يطبع مواده فقط، ويرفض اختيار قسم يخالف قسم الطلب المحدد. في الطلبات العامة/القديمة تُستخدم تصنيفات المواد الحالية، ولذلك يفيد التصنيف الجديد الطلبات السابقة أيضًا. الأسماء والكميات والتاريخ من الطلب المحفوظ، وليس رصيد المخزون الحالي. لا يُعطّل غياب تصنيف قديم طباعة عام.
- الملف A4 طولي عربي مع خط مضمّن وأرقام لاتينية، يعرض رقم الطلب والقسم والموظف وتاريخ الطلب والحالة وجدول المادة والوحدة والمطلوب والواصل والمتبقي للتوريد والملغى، والملاحظات. لا يعرض أسعارًا أو يغيّر حالة الطلب. رؤوس الجدول تتكرر عند امتداده لصفحة جديدة.
- الصلاحيات الجديدة: `mat_classify` للتصنيف، `mat_assign` للتوجيه واختيار الأسماء، `mat_print` للطباعة. لا تُمنح تلقائيًا لأدوار الموظفين الحالية؛ المدير يمتلكها وفق آلية النظام الحالية.
- قائمة الموظف تدمج استعلامين محدودين بطلباته وبالطلبات الموجّهة إليه، بعد تطبيق البحث والحالة والتاريخ ومؤشر الصفحة في كل فرع. يُزال التكرار ثم تُعرض 20 نتيجة. لا يلزم مسح أو ترحيل سجلات قديمة؛ أضيفت أربعة فهارس لفرع `assignedTo`.
- اختبارات الإضافة: خدمة التصنيف والتوجيه وإزالة الوصول، التصفية القديمة والجديدة، 401/403 لمسار الطباعة، رفض التوجيه والتصنيف دون صلاحية، 30 نتيجة مختلطة بلا تكرار عبر الصفحات، واجهة 390/1280، وتحويل PDF فعلي إلى صور ومراجعتها. بيانات الاختبارات محلية فقط.

```powershell
npx tsx --test lib/server/material-requests-core.test.ts
node scripts/test-material-requests-api.mjs
node scripts/test-material-requests-ui.mjs
npm test
npm run build
```

اختبارات الخدمات تستخدم Firestore وهميًا محليًا مع شرط القراءات قبل الكتابات؛ واختبارات API تستخدم الحارس الحقيقي؛ واختبارات المتصفح تستخدم بيانات اختبار على مقاسي الكمبيوتر والجوال. لا تنشئ طلبات أو واردًا تجريبيًا في الإنتاج. النسخ الاحتياطي المحلي يبقى معطلًا بطلب المستخدم.
